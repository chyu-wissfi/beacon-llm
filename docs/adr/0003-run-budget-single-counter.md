# ADR-0003: Run 预算统一计数器，网关是重试的唯一权威

日期：2026-08-30 · 状态：已接受

## 背景

一次调用可能发生三种"再来一次"：瞬时故障重试、Fallback 切换候选端点、校验失败的修复调用。同时所有供应商 SDK 都有内置重试。若各层各自为政，实际上游请求数 = 网关编排次数 × SDK 重试次数，任何"上限"都是假的。

## 决策

1. **Run 预算 = 总尝试上限 4 次 + 墙钟超时（`timeout_seconds`，默认 30s）**。重试、Fallback、修复调用共享同一个尝试计数器与同一个 deadline。
2. **所有供应商 SDK 内置重试一律关闭**（openai `max_retries=0`、anthropic 同理），网关编排层是重试的唯一权威。
3. 退避策略：0.5s 起、每次 ×2、加 0~0.2s 随机抖动；尊重上游 `Retry-After`（有则优先）。
4. 可重试判定：连接错误 / 超时 / 上游 429 / 5xx；其余 4xx 一律不重试（确定性错误）。
5. 不设成本上限（单次调用实时算钱需要读价目表明细，复杂度与收益不匹配），写成演进项。
6. 修复调用单独上限 1 次（消耗预算计数）。

## 理由

"所有再尝试形式消耗同一预算"必须落成**单一数据结构**才可验收：状态机里一个计数器、一个 deadline，终态迁移时 `attempts` 字段就是它的审计值。SDK 重试不关闭则计数器数的是网关视角而非真实上游压力，预算控制失效；抖动防止多实例/多请求同拍退避造成惊群；尊重 `Retry-After` 是因为那是上游亲口说的节奏。

## 后果

正面：预算可测试（Fake Adapter 按剧本计数上游请求数，断言恰好 N 次，同时证明无隐藏重试）；行为对调用方可解释（attempts 字段）。
负面：放弃 SDK 重试的免费实现；成本维度不在预算内（记录在 Trace 但不参与熔断决策）。
