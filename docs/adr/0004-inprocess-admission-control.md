# ADR-0004: 准入控制与熔断采用单进程内存实现，多层拦截在编排之前

日期：2026-08-30 · 状态：已接受

## 背景

LLM 请求是长耗时操作：只限 QPS 挡不住连接堆积（60 RPM 限制下每个请求跑 30 秒，仍会堆出 30 个并发）。生产系统通常需要全局并发、每供应商并发、每模型 RPM/TPM 多层限制。同时本项目明确单实例部署（多副本是非目标）。

## 决策

1. 多层准入控制，全部在请求进入编排之前（`api/` 调 `core/`）：全局并发（信号量，默认 20）→ 每供应商并发（默认 10）→ 每模型 RPM（令牌桶，默认 60）；TPM 采用**调用后按实际 usage 记账**（事后扣减）。
2. 并发计数从准入持有到流式结束，流式请求全程占位。
3. 按模型熔断：连续 5 次失败 → 熔断 30s（503 `circuit_open` 快速失败）→ 半开放行 1 个探测请求，成功闭合。
4. 全部状态存进程内存（信号量、桶、计数器、熔断状态机）。多副本部署需迁移到 Redis 等共享存储——**这是明示的演进路径，不是缺陷**。
5. 阈值全部为配置项（`config/models.yaml`），不是代码常量。

## 理由

内存实现与单实例部署假设自洽，且信号量/令牌桶在进程内是最简正确的实现。TPM 事后记账而非预估扣减：调用前输出长度未知，按 `max_tokens` 预留会把限流收得过死（调用方设 max_tokens=4096 而实际输出 200 token，预留式会误伤一个数量级）。熔断窗口 30s 与预算时间尺度（4 次尝试 × 最多几秒退避）错开，不互相打架。

## 后果

正面：实现简单、无外部依赖、单进程内对所有请求即时可见。
负面：重启丢状态（可接受：熔断/限流是保护机制非记账数据）；多副本时全部失效，迁移 Redis 是既定演进路径；TPM 事后记账对突发尖峰的抑制是滞后的（第一个窗口可能超）。
